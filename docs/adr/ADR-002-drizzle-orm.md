# ADR-002: Use Drizzle ORM with PostgreSQL

**Status:** Accepted  
**Date:** 2025-04-27  
**Confidence:** High

---

## Context

The platform requires a typed database access layer for PostgreSQL with schema management and migration support.

---

## Decision

Use **Drizzle ORM** with the `node-postgres` (pg) driver.

---

## Alternatives Considered

| ORM/Library | Reason Not Chosen |
|-------------|------------------|
| Prisma | Runtime abstraction layer adds latency on hot paths; schema lives in `.prisma` file (separate from TypeScript); migration workflow more complex |
| TypeORM | Decorator-based; requires `experimentalDecorators`; heavier runtime |
| Kysely | Query builder only; no schema management |
| Raw `pg` | No type safety; schema drift risk |
| Knex.js | No native TypeScript types; aging ecosystem |

---

## Tradeoffs

| Pro | Con |
|-----|-----|
| TypeScript schema is source of truth | No DataMapper pattern — business logic mixed with route handlers |
| Lightweight runtime (no proxy magic) | Less abstraction — SQL knowledge required |
| SQL-like query API — readable | No built-in soft deletes or audit plugins |
| drizzle-zod integration for Zod schema generation | |
| Fast migrations via drizzle-kit | |

---

## Consequences

- `lib/db/src/schema/` is the single authoritative definition of all database tables
- `drizzle-zod` generates `insertSchema` / `selectType` from table definitions
- Migrations are generated by `pnpm --filter @workspace/db run generate` and applied by `run migrate`
- No repository layer — route handlers query `db` directly
- JSON columns typed as `jsonb` with `.$type<T>()` for TypeScript safety
