# Technical Audit Report — 18 November 2026

**Scope:** whole application at commit `f27070f` (React frontend, Express API, PostgreSQL schema and queries, configuration and docs), with extra depth on code added since the previous audit (`7f53b32`, 10 Nov 2026: about 26,000 lines: Live Twin, Data Management, Visualization library, languages, Home, Access Control modules).
**Method:** read-only static review by five parallel reviewers (authentication and access, API and configuration, database and performance, frontend, end-to-end workflows), followed by personal verification of every HIGH finding against the code. Dependency scan with `pnpm audit`. Typecheck and the 64 API regression tests were run and pass.
**Not done:** no live attack testing. The only configured database is the local `integrated_suite`, which may hold real data, and the audit rules forbid touching it. No browser walkthrough. Every finding below comes from reading the code; "Confirmed" means the faulty path was traced line by line, "Potential" means it depends on data volume, timing or deployment.

## B. Architecture assessment

- **React:** a single SPA (React 19, Vite, TanStack Query) with a generated API client. Route guards mirror the server rules for usability only; the server is authoritative, as it should be. No XSS sinks with user data, no secrets in the bundle, and writes go through `apiFetch` with CSRF. The weak spots are state races in the new Live Twin editors and some widget sizing and caching bugs.
- **Express:** a clear middleware chain (`attachPrincipal → attachApiClient → stripForgedActorHeaders → csrfGuard → authorize → projectScopeGuard`), global body and structure limits, and a correlation-id error handler. The weaknesses are per-object checks that newer routes skip (API-client ceiling, uploads, twin project), and long synchronous jobs run inside requests.
- **PostgreSQL:** Drizzle schema, pooled connections (max 10, 30 s statement timeout), and optional monthly telemetry partitions with summaries and archives. The weaknesses are missing uniqueness on telemetry and attributes, missing indexes on hot lookups, and partition maintenance that needs table-owner rights the documented runtime role does not have.
- **Cross-layer:** OpenAPI codegen keeps the contract consistent. The hand-written Data Management and Live Twin calls match `ROUTE_RULES`. One mismatch: the Live Twin page calls APIs gated on other modules (FE-5).

## D–E. Detailed findings (HIGH)

### AUTH-1 — Engineer can take over an admin's full-access API key
- **Affected:** `artifacts/api-server/src/routes/api_clients.ts` — `PUT /api-clients/:id` (~line 363), `POST /api-clients/:id/rotate-secret` (line 486), `/restore` (~592), DELETE; guard `refuseIfOutOfScope` (line 78).
- **Current:** the scope ceiling (`ungrantableScopes`) runs on create and on PUT only for scopes being *added*. Rotate, restore, delete and PUT changes to `allowedIps`, `expiresAt`, `projectId` check only project scope. Engineers and Developers hold `manage_api_clients` by default (`lib/rbac.ts`).
- **Reproduction:** as an unrestricted Engineer, `PUT /api/api-clients/<admin key id>` with `{"allowedIps":[],"expiresAt":null}`, then `POST /api/api-clients/<id>/rotate-secret`. The response carries a new secret for a `*` or `read:*` key.
- **Root cause:** the per-object check covers which project, not how powerful the key is.
- **Impact:** persistent, IP-unrestricted read access to every project's telemetry, alarms and assets via `/export/*`, outliving the user's session and role; `/restore` revives keys an admin revoked.
- **Fix:** add `refuseIfScopeAboveCaller(req, client)` using `ungrantableScopes(access, client.scopes)` (treat empty scopes as `*`) and call it in PUT, rotate-secret, regenerate-ingest-url, restore and DELETE; log refusals as `authz.denied`.
- **Enhancement:** return ingest URLs only through an audited "reveal" action (AUTH-9).
- **Test:** Engineer gets 403 rotating or editing a `*` or `read:telemetry` key, 200 on an `ingest:write` key.

### DB-2 / FN-7 — Asset delete bypasses legal holds
- **Affected:** `routes/assets.ts:231-233` (`tx.delete(telemetryTable)…`, `tx.delete(telemetryRollupsTable)…`).
- **Current:** no `activeHolds()` check; `telemetry_rollups_15m` never deleted; the whole delete is one transaction under the 30 s statement timeout.
- **Reproduction:** place a hold on asset X, delete X or its project; the held readings are gone. Delete a project with tens of millions of readings; it times out and rolls back every time.
- **Impact:** compliance failure (the screen promises "readings under a hold are never deleted"); orphan summaries keep showing in charts; big projects cannot be deleted.
- **Fix:** refuse with 409 `hold_conflict` when a hold covers any asset in the subtree (or a time-only hold covers its data); delete `telemetry_rollups_15m` too; delete metadata in the transaction and telemetry afterwards in batches (reuse `deleteInBatches`).
- **Test:** hold on asset, DELETE gives 409; 15-minute summary count for the asset is 0 after a delete.

### FN-1 / AUTH-3 / API-2 / FN-4 — Approval and hold bypasses
- **Affected:** `routes/system.ts:611` (DELETE policy, no approval, no `validate`); `routes/data_ops.ts:40-50` (data settings: approval on/off, threshold, tier days); `data_ops.ts:323` (hold release); `system.ts:570/592/621` (approval only `if (rollupsEnabled())`).
- **Current:** a single user with `manage_assets` + Reports write (Engineer by default) can switch approval off, raise the threshold, release a hold, delete a protective policy, or split a deletion into sub-threshold requests. The retention screen tells the user approval is needed while the server deletes at once.
- **Reproduction:** global 30-day policy plus asset X 365-day policy, approval on. Delete X's policy: 204, and the next hourly run deletes X's older readings with no approval.
- **Impact:** permanent deletion of telemetry, including held data, by one person, which defeats both controls.
- **Fix:** route policy delete through `approvalRequired`/`requestApproval`; when approval is on, make disabling it, raising the threshold, lowering tier days and releasing a hold into pending requests a different administrator approves; fail closed when no estimate is available; total requested rows per requester over a rolling window.
- **Test:** with approval on, each of these returns 202 pending and changes nothing until a second admin approves; self-approval returns 403.

### FN-2 — Archive restore crashes the API
- **Affected:** `services/archive.ts:154` (`createInterface({ input: createReadStream(file).pipe(createGunzip()) })`); also `routes/data_ops.ts` download `createReadStream(file).pipe(res)`.
- **Root cause:** `.pipe()` does not forward the read stream's `error`; an ENOENT or EACCES becomes an uncaught exception, and `index.ts` exits the process on uncaught exceptions.
- **Reproduction:** archive a day, remove the `.jsonl.gz` (or the network share drops), click Restore.
- **Impact:** whole platform down (ingest, MQTT, WebSocket) until systemd restarts it; repeatable by anyone allowed to restore.
- **Fix:** `stat` the file first (410 `archive_file_missing`, as download already does) and use `stream/promises.pipeline`; verify the stored SHA-256 before inserting (API-9); create the hold before inserting rows (FN-14).
- **Test:** restore with file removed returns 410 and the process stays up; a modified file returns 422 with 0 rows inserted.

### DB-1 — Documented DB roles break partitioning, pruning and backups
- **Affected:** `.env.example:298-305` ("The API runs no DDL at runtime"); `services/partitions.ts:73,99-100` (CREATE/DROP TABLE); `routes/data_ops.ts:214` (VACUUM); `routes/system.ts:885-895`; `docs/operations/backup-restore.md:34-38`.
- **Current:** once `partition-telemetry` has run, the runtime role cannot create next month's partition (readings pile into the default partition, which later blocks creating that month), `dropExpiredPartitions` throws *before* the row-delete loop so all telemetry pruning stops, `pg_dump` as the backup role fails on schema `telemetry_parts`, and VACUUM silently skips tables it does not own.
- **Impact:** unbounded telemetry growth and failed backups on a correctly hardened installation.
- **Fix:** correct `.env.example`; run partition maintenance as a privileged scheduled job (or document the ownership trade-off); wrap partition drop in try/catch so row deletes still run; add `GRANT USAGE ON SCHEMA telemetry_parts …` and default privileges for the runtime and backup roles in both docs.
- **Test:** on a staging DB with the two roles, convert to partitions, run scheduled retention and the backup script; both succeed.

### FE-1 — Live Twin saves into the wrong twin
- **Affected:** `artifacts/iot-platform/src/features/plantTwin/PlantTwinView.tsx:102-108` (`doSave`), `:143-163` (load effect).
- **Current:** `currentRef.current` switches to the new twin immediately, but `canEditRef` and the engine's scene change only after the GET succeeds. Save stays clickable during loading (the overlay covers only the stage), and after a failed load.
- **Reproduction:** open editable twin A, select editable twin B on a slow network, press Save: `PUT /plant-twins/B` is sent with A's scene. Or let B's load fail, then edit or leave the page.
- **Impact:** B's layout, machine links and areas silently replaced; no undo. Same pattern in `tagTwin/TagTwinView.tsx` (FE-2).
- **Fix:** set `canEditRef.current = false` and `loadingRef.current = true` at the start of the load; keep a `loadedIdRef` set only after `loadScene` succeeds and refuse to save unless it equals `currentRef.current`; disable Save while loading or after a load error. Add the server-side `expectedUpdatedAt` conflict check (FN-12).
- **Test:** throttle network, switch twins, press Save; no PUT is sent until the new twin has loaded.

## F. Authentication and authorization report

Login, sessions, password reset and activation are sound (hashed 256-bit tokens, single use, expiry, idle and absolute session limits, rechecked on every request, generic login errors with timing equalisation, layered rate limits). CSRF is double-submit and bound to the session. The route table is deny-by-default and every route was mapped with no gaps or ordering bugs. Project scoping covers assets, telemetry, alarms, activity log, ingest and (since `f27070f`) exports.

Gaps: AUTH-1 (API-key ceiling on existing keys), AUTH-2 (uploads), AUTH-3 (approval controls governed by the people they restrain), AUTH-4 (lockout used to end live sessions), AUTH-5 (WebSocket after expiry), AUTH-6/7 (dashboard and twin visibility widening), AUTH-8 (Access Control options that do nothing).

## G. Data protection and encryption report

Strong: scrypt passwords; SHA-256 session, token and API-key hashes; AES-256-GCM for broker passwords, destination credentials and ingest tokens with key rotation; secrets from files; production refuses to start without the encryption key; logs redact cookies, auth headers and passwords; backups are gpg-encrypted.

Gaps: alarm and alert webhook URLs stored and logged in clear (API-6); raw SQL and paths in stored error text (API-3); archive files unencrypted and unverified (API-9); server paths and other sessions' SQL in responses (API-11); GCM tag length not pinned (API-13); personal data in activity and security logs kept after user deletion (document it in the privacy notes).

## H. API and database assessment

API: parameterised SQL throughout, explicit field lists (no mass assignment), global body and structure limits, consistent error format. Gaps: unbounded `limit` (PERF-2), MQTT limits (API-4), unsafe alert webhook (API-1), long synchronous jobs (FN-11).

Database: good pool settings, TLS support, one-open-alarm unique index, optimistic locking on Visualization. Gaps: no telemetry uniqueness (DB-4), no attribute uniqueness (DB-6), missing indexes (PERF-4), non-atomic multi-step writes (DB-5, DB-8, FN-6), privilege model vs partitioning (DB-1), late data vs archive and summaries (DB-3).

## I. Performance and reliability report

Hot path: ingest does 3 full asset-table loads plus about 6 round trips per machine per payload (PERF-1). Analytics can monopolise the pool (API-7). The metric list and some exports scan far more than needed (PERF-3, PERF-5). Reliability: archive restore crash (FN-2), stuck VACUUM flag (API-8), pruning window timing (FN-9), lost rejection counts (FN-15), GPU memory growth in long Live Twin sessions (FE-11).

## J. Technical enhancement recommendations

1. An in-process asset-tree cache, invalidated on asset writes; the single-process design already allows it. Removes most per-request full-table loads.
2. Background-job pattern (202 plus status polling) for archive, restore, large deletes and VACUUM; add `proxy_read_timeout` to the nginx guide.
3. One shared "governed change" helper so every destructive Data Management action, and every change to the controls themselves, goes through the same approval path.
4. Idempotent ingest: a unique `(asset_id, metric, timestamp)` key plus `ON CONFLICT DO NOTHING`.
5. A `late_ranges` record at ingest so summaries and archives are redone for backfilled periods.
6. Optimistic version checks (`expectedUpdatedAt`) for every editable JSON document (twins now, others later).
7. A lint rule or test that every outbound `fetch` goes through `safeFetch`, and every CSV through `csvCell`.

## L. Final production readiness assessment

**CONDITIONALLY READY – REMAINING RISKS DOCUMENTED.**

The security foundations are solid, there is no critical vulnerability, and the issues fixed in the November audit stay fixed. The six HIGH issues are, however, real and reachable by ordinary users (Engineer role, or anyone allowed to restore an archive). They concentrate in features added since that audit (Data Management, Live Twin, the API-client changes) and they touch exactly what a paying customer relies on: their data, their legal holds and platform uptime. The condition is that the P0 list is fixed and retested before the platform is installed for another company. P1 should follow within the next release.

**Untested areas:** no runtime or penetration testing (no isolated database available); no browser walkthrough; nginx, systemd and journald permissions on a real VM; MQTT broker access control; email delivery; the partition conversion script under load; AI prompt-injection behaviour; calculation correctness of every pro widget; older pages unchanged since 7f53b32 were only spot-checked.

Per the audit rules, nothing has been changed in the code. Fixes start only after these findings are reviewed and approved. Each fix will then get a regression test and a verification report.
