## B. Architecture assessment

- **React:**
  - A single SPA (React 19, Vite, TanStack Query) with a generated API client.
  - Route guards mirror the server rules for usability only; the server stays authoritative.
  - The session lives in an HttpOnly cookie and the CSRF token in memory. All writes go through `apiFetch`, and no secrets are in the bundle.
  - New screens (Live Twin builders, AI Reports, Audit Log, Live Feed) are large, single-file components. Their load/save state handling is the weak spot (H-6, M-18).
- **Express:**
  - A clear middleware chain: `floodGuard → attachPrincipal → attachApiClient → stripForgedActorHeaders → audit context → csrfGuard → authorize → projectScopeGuard → apiRateLimit`.
  - Global body and structure limits, and a correlation-id error handler.
  - Weak points:
    - Per-object rules on newer resources (API keys, uploads, Data Management approvals).
    - Simple boolean modules silently ignore the `level` the route table asks for (H-2).
- **PostgreSQL:**
  - Drizzle schema with pooled connections (max 10, 30 s statement timeout), optional monthly telemetry partitions, and hourly and 15-minute summaries.
  - Weak points:
    - Missing uniqueness on telemetry and missing indexes on hot lookups.
    - The audit log's protections live in data the runtime login can rewrite (H-7).
    - The schema is applied by `push`, so DDL such as the audit trigger is run by the app at start-up (H-5).
- **Cross-layer:**
  - OpenAPI codegen keeps the contract consistent.
  - The hand-written AI Report, Audit Log and Live Feed calls match the server responses field for field.
  - Mismatches:
    - The global request guard (20k keys) refuses scenes the plant-twin route allows (40k) (M-15).
    - Live Feed's request pattern exceeds the server's rate limiter (H-8).

## D–E. Detailed findings (HIGH)

Each finding uses the 14-point format.

### H-1 — An Engineer can take over an administrator's full-access API key
1. **ID:** H-1 (AUTH-1, API-1; 18 Nov AUTH-1).
2. **Description:**
   - Rotate-secret, PUT, restore and delete on API keys never compare the key's scopes with what the caller is allowed to grant.
   - An Engineer (scope ceiling `ingest:write`) can therefore rotate an admin's `*` key and receive the new secret.
3. **Severity:** HIGH (security remediation).
4. **Technology:** Express API.
5. **Affected:**
   - `artifacts/api-server/src/routes/api_clients.ts:489-510` (rotate-secret), `:364-486` (PUT), `:595-610` (restore).
   - `refuseIfOutOfScope` at `:79-91`.
   - Route rules at `middleware/authorize.ts:173-176`.
6. **Current implementation:** `refuseIfOutOfScope` returns `false` immediately for any user who is not project-restricted. Rotate then issues `randomUUID()` and returns it as `clientSecret`. `ungrantableScopes` is used only on create and on scope additions in PUT.
7. **Expected implementation:** a user may act on a key only if every scope on it is one they could grant themselves.
8. **Root cause:** the scope ceiling covers creating and widening keys, but not acting on existing wider keys.
9. **Impact:** a lasting credential that can read all assets, telemetry and alarms through `/export/*` and post to ingest. It also breaks the admin's integration and allows revoked keys to be revived.
10. **Fix:** in rotate, regenerate-ingest-url, restore, delete and PUT (for every field), return 404 when `ungrantableScopes(access, client.scopes).length > 0`.
11. **Enhancement:** show "managed by an administrator" on such keys in the UI, and record an audit alert when a `*` key is rotated.
12. **Approach:** one helper `refuseIfAboveCeiling(req, res, client)`, called after the row is loaded in each handler.
13. **Test:**
    - A new API test: as an Engineer, rotate an admin `*` key and expect 404.
    - As an Admin, expect 200.
14. **Expected outcome:** key management is limited to keys within the caller's own grant level.

### H-2 — Two-person approval and legal holds can be bypassed
1. **ID:** H-2 (AUTH-2, FN-1, FN-2; 18 Nov FN-1/AUTH-3/API-2/FN-4).
2. **Description:** one Engineer can turn approval off, release any legal hold, approve another person's deletion, delete retention policies, and then range-delete telemetry.
3. **Severity:** HIGH (security remediation, business logic).
4. **Technology:** Express API, RBAC.
5. **Affected:**
   - `routes/data_ops.ts:41-54` (PUT data-settings), `:327-334` (hold release), `:434-454` (range-delete).
   - `routes/system.ts:574,594,615-625` (policy delete; approval skipped when `rollupsEnabled()` is false).
   - `middleware/authorize.ts:260-283`.
   - `lib/rbac.ts:391-402` (`hasModuleAccess`).
6. **Current implementation:**
   - The rules ask for `permission: "manage_assets", module: "data_management", level: "delete"`.
   - `data_management` is a simple boolean module, and `hasModuleAccess` returns the boolean regardless of level.
   - Engineer and Developer hold both `manage_assets` and `data_management: true` by default.
   - Hold release has no check of who created the hold.
7. **Expected implementation:**
   - Only administrators, or an explicit grant, can approve, reject, release holds, change approval settings or delete policies.
   - Changes to approval settings and hold release themselves need a second person.
   - Approval fails closed when estimates are unavailable.
8. **Root cause:**
   - The people the controls are meant to restrain are the ones who run them.
   - The rule table's `level` silently degrades to "read" on simple modules.
9. **Impact:** evidence under legal hold, and history, can be destroyed by one person. This defeats the feature's purpose and any compliance claim built on it.
10. **Fix:**
    - Add a permission `approve_data_changes` (admin roles only). Require it for approve, reject, hold release, `PUT /system/data-settings` and policy DELETE.
    - Route approval-setting changes and hold release through `requestApproval`, with the requester barred from approving.
    - Fail closed when rollups are off.
11. **Enhancement:** make `authorize` refuse at start-up any rule that sets `level` on a simple module, so this class of bug cannot return.
12. **Approach:** RBAC constant plus route-table changes; small handler changes in `data_ops.ts` and `system.ts`; a start-up assertion in `authorize.ts`.
13. **Test:** API tests as an Engineer for each of the five endpoints, expecting 403. The requester approving their own request gets 403. A test that a rule with `level` on a simple module throws.
14. **Expected outcome:** the two-person rule and legal holds actually hold.

### H-3 — Deleting an asset ignores legal holds
1. **ID:** H-3 (DB-2, FN-2; 18 Nov DB-2/FN-7).
2. **Description:** deleting an asset or project deletes its telemetry even when a legal hold covers it. It leaves the 15-minute summaries behind. The single telemetry delete times out on large projects.
3. **Severity:** HIGH (security remediation, data integrity).
4. **Technology:** Express API, PostgreSQL.
5. **Affected:** `routes/assets.ts:219-267`.
6. **Current implementation:** a recursive CTE collects the subtree, then telemetry, rollups and metadata are deleted in one transaction under the 30 s statement timeout. There is no `activeHolds()` call, and `telemetry_rollups_15m` is not deleted.
7. **Expected implementation:** refuse with 409 `hold_conflict` when any asset in the subtree is under hold. Delete all summary tiers. Delete telemetry in batches outside the metadata transaction.
8. **Root cause:** the asset delete was written before holds and 15-minute summaries existed, and was never updated.
9. **Impact:** held evidence is destroyed. Orphaned summaries keep appearing in charts. Large projects cannot be deleted.
10. **Fix:** call the hold check before the transaction, add the `telemetry_rollups_15m` delete, and move the telemetry delete to `deleteInBatches` after commit.
11. **Enhancement:** run large deletes as a background job with progress shown in Data Management.
12. **Approach:** reuse `holdConflict`/`activeHolds` and `deleteInBatches` from `data_ops.ts`/`system.ts`.
13. **Test:** an API test where an asset under hold gets DELETE 409. A test that the 15-minute summary rows are gone after delete.
14. **Expected outcome:** holds are honoured everywhere data can be deleted.

### H-4 — A missing archive file crashes the API
1. **ID:** H-4 (API-1, FN-3; 18 Nov FN-2).
2. **Description:** restoring an archive whose file has been moved or deleted emits an unhandled stream error. `uncaughtException` then exits the process.
3. **Severity:** HIGH (bug fix, availability).
4. **Technology:** Node.js streams.
5. **Affected:**
   - `services/archive.ts:154` (`createReadStream(file).pipe(createGunzip())`, no `stat`, no error listener).
   - `routes/data_ops.ts:354` (download pipe without an error handler).
   - `index.ts:34-37`.
6. **Current implementation:** the restore opens the file without checking it exists. The read-stream `error` is not handled, and the process exits.
7. **Expected implementation:** return 410 `archive_file_missing`, and handle every stream error.
8. **Root cause:** `.pipe()` does not forward errors, and no listener is attached.
9. **Impact:** ingest, MQTT and every live screen go down until systemd restarts the service. Any Data Management writer can trigger it repeatedly.
10. **Fix:** `stat` before restore, and use `stream/promises.pipeline` for both restore and download.
11. **Enhancement:** verify the stored SHA-256 before inserting rows, and create the hold before inserting (18 Nov FN-14).
12. **Approach:** small changes in two files.
13. **Test:** a unit or API test that restoring an archive whose file was deleted returns 410 and the process stays up.
14. **Expected outcome:** archive problems produce an error message, not an outage.

### H-5 — The documented DB roles break partitioning, backups and the audit trigger
1. **ID:** H-5 (DB-3; 18 Nov DB-1).
2. **Description:** `.env.example` and the backup guide describe a runtime role without DDL rights. With that role:
   - partition creation and drop fail;
   - pruning stops;
   - backups miss `telemetry_parts`;
   - the new audit trigger is never created, while the UI still describes the log as append-only.
3. **Severity:** HIGH (configuration, preventive measure).
4. **Technology:** PostgreSQL, ops docs.
5. **Affected:**
   - `.env.example:303`.
   - `services/partitions.ts:100` (`DROP TABLE` without try/catch).
   - `routes/system.ts:891-899`.
   - `docs/operations/backup-restore.md:34-38`.
   - `lib/audit-store.ts:157-171` (`ensureAuditStore` runs `CREATE FUNCTION`/`CREATE TRIGGER` at every start).
6. **Current implementation:** DDL runs at runtime. Failures are only logged with "run db push", and `ensured` is reset, so every prune and verify retries the DDL.
7. **Expected implementation:**
   - DDL is applied by an owner-run step.
   - At start-up the app only checks that the trigger exists, and raises a system alert if it does not.
   - The docs and grants match reality.
8. **Root cause:** schema management by `push` plus runtime DDL, combined with docs written for a migration-based setup.
9. **Impact:** installations that follow the hardening guide silently lose pruning, backups of partitions and audit-log protection.
10. **Fix:**
    - Move `GUARD_SQL` into an owner-run script (`pnpm --filter @workspace/db run audit-guard`).
    - Check `pg_trigger` at start-up.
    - Add `USAGE` on `telemetry_parts` to the grants.
    - Wrap the partition drop in try/catch.
11. **Enhancement:** adopt the prepared migration workflow (`docs/operations/database-migrations.md`) so all DDL is versioned.
12. **Approach:** a DB package script, docs updates, small API changes.
13. **Test:** on a scratch database with the documented runtime role, start the API: a system alert is raised if the trigger is missing, and pruning and partition maintenance complete.
14. **Expected outcome:** hardened installations work and do not silently lose protections.

### H-6 — Live Twin saves into the wrong twin
1. **ID:** H-6 (FE-2, FN-7; 18 Nov FE-1).
2. **Description:** when switching twins, the selected id changes at once, but the 3D engine still holds the previous twin's scene and edit right until the new twin loads, and forever if the load fails. Pressing Save writes twin A's layout into twin B. The 2D twin view has the same flaw.
3. **Severity:** HIGH (bug fix, data integrity).
4. **Technology:** React, Express API.
5. **Affected:**
   - `iot-platform/src/features/plantTwin/PlantTwinView.tsx:117-123` (`doSave`), `:160-182` (load effect), `:386` (Save button).
   - `features/imageTwin/ImageTwinView.tsx:137,153-163,190-195,356`.
   - `api-server/src/routes/plant_twins.ts:210-245` (no version check).
6. **Current implementation:**
   - `currentRef.current = currentId` is set immediately, while `canEditRef` keeps the old value.
   - The load error path only shows a toast.
   - Save is disabled only while saving.
   - The server accepts any PUT.
7. **Expected implementation:** Save is allowed only when the loaded twin equals the selected twin. The server refuses stale writes with 409.
8. **Root cause:** there is no "loaded id" state separate from the "selected id", and no optimistic locking on the server.
9. **Impact:** silent loss of a twin's layout and its machine bindings, with no undo.
10. **Fix:**
    - At effect start, set `canEditRef=false`, `loadingRef=true` and `loadedIdRef=null`. Set `loadedIdRef` only after `loadScene` succeeds.
    - `doSave` refuses unless `loadedIdRef === currentRef.current`.
    - Disable Save while loading or after an error.
    - Add an `expectedUpdatedAt` check with `SELECT … FOR UPDATE` on the server, as `viz_nodes` does.
11. **Enhancement:** keep a short version history per twin so mistakes can be undone.
12. **Approach:** the same guard in PlantTwinView, ImageTwinView and TagTwinView (see M-18); a server change plus an OpenAPI field.
13. **Test:**
    - Manual with a throttled network: switch twins and press Save; no PUT is sent until load resolves, or when it fails.
    - An API test: a PUT with a stale `expectedUpdatedAt` returns 409.
14. **Expected outcome:** no cross-twin overwrites.

### H-7 — The audit log's tamper evidence can be bypassed
1. **ID:** H-7 (DB-1, DB-5).
2. **Description:** anyone who can run SQL with the app's own login can bypass the append-only trigger and the hash chain:
   - by setting the session variable `app.audit_retention='on'`;
   - by inserting rows (no insert guard);
   - by editing the pruning checkpoint in `job_state`;
   - by recomputing the unkeyed SHA-256 chain.

   The backfill also hashes forged unhashed rows on the next write.
3. **Severity:** HIGH (security remediation; compliance accuracy).
4. **Technology:** PostgreSQL, Express API.
5. **Affected:**
   - `lib/audit-store.ts:88-109` (`GUARD_SQL`), `:124-153` (backfill and `chainHead`), `:325-343` (prune), `:81-83` (checkpoint).
   - `lib/audit-core.ts:126` (`entryHash`).
   - `docs/security/compliance.md:19` and `docs/features/audit-log.md` (claims).
6. **Current implementation:**
   - The trigger allows DELETE whenever `current_setting('app.audit_retention', true) = 'on'`, which any session can set.
   - The trigger covers UPDATE, DELETE and TRUNCATE only.
   - The checkpoint is an ordinary row, and the hash has no secret key.
7. **Expected implementation:** the runtime role cannot delete or update audit rows or the checkpoint. Inserts must carry a valid chain link. The chain head is anchored outside the database with a keyed MAC.
8. **Root cause:** the protections live in data and settings that the runtime login can change.
9. **Impact:**
   - With the credentials in `.env` (a shell on the VM, or a future SQL injection), entries can be deleted, rewritten or forged without detection.
   - The docs present the log as a 21 CFR Part 11 / ISO 27001 control, which overstates it.
10. **Fix:**
    - `REVOKE UPDATE, DELETE, TRUNCATE ON activity_logs, job_state FROM <runtime role>`.
    - Prune through a `SECURITY DEFINER` function owned by the table owner that deletes only rows older than the retention period, and writes the checkpoint to an insert-only table.
    - In the trigger, check `current_user` instead of a session setting.
    - Add a `BEFORE INSERT` trigger that rejects a NULL `seq` or `hash` and a mismatched `prev_hash`.
    - Run the backfill once only, from start-up, up to a stored marker; `ORDER BY seq DESC NULLS LAST`; make `seq` NOT NULL.
11. **Enhancement:**
    - Use an HMAC keyed from `SECRETS_ENC_KEY` and sign the checkpoint.
    - Ship the chain head `(seq, hash, mac)` outside the database periodically, for example in the backup manifest or to syslog.
    - Verify fails if the head goes backwards.
    - Correct the compliance docs until this is in place.
12. **Approach:** an owner-run SQL script (together with H-5), a small change in `audit-store.ts`, docs updates.
13. **Test:** on a scratch database as the runtime role:
    - `SET app.audit_retention='on'; DELETE FROM activity_logs` fails with 42501.
    - An insert with a NULL hash fails.
    - Editing the checkpoint makes verify fail.
14. **Expected outcome:** tampering needs the DB owner credentials and is still detectable from the external anchor.

### H-8 — Live Feed exhausts the API rate limit
1. **ID:** H-8 (FE-1, DB-4, FN-5).
2. **Description:** every 30 s, Live Feed requests `/assets/:id/health` and `/assets/:id/attributes` for every asset in scope. That is 4 requests per asset per minute per tab. The per-user (and per-IP) budget is 600 per minute, so it runs out at about 150 assets. Failed polls are silently ignored, so assets drift to "delayed" or "offline" while data is arriving.
3. **Severity:** HIGH (performance, functional defect).
4. **Technology:** React, Express API, PostgreSQL.
5. **Affected:**
   - `iot-platform/src/features/liveFeed/useLiveData.ts:26-28,134-204`.
   - `api-server/src/middleware/apiRateLimit.ts:53-63`.
   - `lib/auth-config.ts:169`.
   - `routes/ingest.ts:1369-1402` (4 queries per health call).
   - `lib/project-access.ts:32` (loads the whole assets table per request for restricted users).
6. **Current implementation:**
   - The page makes N+1 requests per asset.
   - About 10 to 11 DB queries per asset per 30 s per tab, on a 10-connection pool shared with ingest.
   - Each 429 writes a `ratelimit.tripped` security event.
7. **Expected implementation:** one batched request per poll. Failures show "status unknown" instead of ageing the assets.
8. **Root cause:** per-asset polling designed without considering the rate limiter or pool size.
9. **Impact:**
   - With large plants, every other screen gets 429 errors.
   - Two operators behind one NAT run out at about 75 assets each.
   - The status shown is wrong, false "offline" events are recorded, and the security log fills up.
10. **Fix:**
    - Add `POST /assets/live-summary {ids}` (or project-scoped). It returns per asset: newest reading time, open alarm count, latest attributes and expected interval, from three set queries (attributes `= ANY`, alarms `GROUP BY`, and a `LATERAL` newest-reading lookup as `/sites` uses). Add spec, codegen, a ROUTE_RULES entry and a test.
    - Poll it every 30 s and rely on the WebSocket in between.
    - Cache `assetScope` per user for a few seconds.
11. **Enhancement:** back off on 429, poll only visible assets, and show a "data could not be refreshed" banner.
12. **Approach:** a server endpoint plus a `useLiveData` rewrite of the poll function.
13. **Test:** with 200 mocked assets, at most 2 requests per poll. A unit test that a 429 does not turn assets offline. On the server, a test that 30 polls stay under the limiter.
14. **Expected outcome:** Live Feed scales to thousands of assets without affecting other screens.

## F. Authentication and authorization report

**Sound:**
- **Sessions:** HttpOnly cookie with idle and absolute expiry.
- **CSRF:** double-submit token bound to the session.
- **Login:** origin guard, dummy scrypt for timing, rate limits per IP, subnet and account.
- **Tokens:** activation and reset tokens are hashed, single-use and rate-limited.
- **Session revocation:** on password change or reset, temporary password and suspension.
- **Route table:** deny-by-default with full method coverage; `AUTH_ENFORCE=false` is refused in production.
- **User administration:** rank checks and a last-admin guard.
- **API keys:** hashed, with expiry, CIDR allowlist and scope checks.
- **Project scope:** enforced on direct ids, owner lookups and filtered lists.
- **AI routes:** scope intersected with project access, and every tool enforces it.
- **Audit endpoints:** verify, settings and acknowledge require `manage_security`.

**Open:**
- H-1 (API keys) and H-2 (approvals).
- M-1 (lockout ends sessions).
- M-2 (uploads), M-3 (security events), M-4 (attention endpoint).
- M-5 (restricted admin), M-21 (sockets after delete or expiry).
- L-1 to L-4.
- No MFA: `otpLimiter` exists but is not mounted.

## G. Data protection and encryption report

**Sound:**
- **Passwords:** scrypt.
- **Hashes:** SHA-256 for sessions, tokens and API keys.
- **Integration secrets:** AES-256-GCM with per-field AAD and key rotation (brokers, destinations, ingest tokens). Production refuses to start without `SECRETS_ENC_KEY`.
- **Responses:** never include password, MFA or secret fields.
- **Logs:** pino redacts cookies, authorization headers, tokens and passwords.
- **Audit diffs:** redact secret-named fields at any depth.
- **Downloads:** sandboxed with attachment and nosniff.

**Open:**
- M-6 (webhook secrets kept permanently in the audit log).
- L-8 (webhook URLs logged in full and stored unencrypted).
- H-7 (audit log integrity).
- I-2 (data sent to Groq needs to be documented for customers).
- I-4 (`.env` synced to OneDrive).
- I-7 (personal data in the append-only log).
- L-26 (plaintext `mfa_secret`, unused).

## H. API and database assessment

**API:**
- **Validation:** consistent use of `validate`/zod. A few routes return 500 on bad input (L-18).
- **SQL:** parameterised everywhere. `sql.raw` is used only with internal constants, and user LIKE input is escaped.
- **Outbound calls:** the URL guard covers webhooks and destinations, but not brokers (M-7) or the Data Management alert webhook (M-8).
- **Uploads:** content-sniffed against an allow-list, polyglots refused, UUID file names.

**Database:**
- **Strong:** rollup design and boundaries, report merge logic (no double counting), optimistic locking on viz nodes, the data-change claim. No deadlock risk among the 6 server-side transactions.
- **Weak:** missing uniqueness and indexes (M-17), plant-twin scene storage (M-14), audit-log search and verify cost (M-12, M-13), late-data summarisation (M-16), report truncation (M-11).

## I. Performance and reliability report

The heaviest problems:
- H-8 (Live Feed request amplification).
- M-14 (plant-twin list reads every scene, up to about 900 KB each).
- M-12 and M-13 (audit-log search, count, export and verify on a table with at least a year of entries).
- M-23 (audit lock during pruning).
- L-25 (parallel query bursts on a 10-connection pool).
- M-22 (nginx timeouts for AI requests).

Reliability:
- **Breaks the service:** H-4 (crash on a missing archive file).
- **Fail silently:** M-20 (pruning stops at the first failing table), L-13 (audit export and verify).

Graceful shutdown, statement timeouts, outbound timeouts and rollup slicing are all in place.

## J. Technical enhancement recommendations

1. **Batched read endpoints for live screens** (Live Feed, Map, twins), with WebSocket push in between; no per-entity polling.
2. **Move DDL out of runtime.** Adopt the prepared migration workflow and run trigger and grant setup as an owner step (H-5, H-7).
3. **Store large binary content (2D-twin images, GLB) in `uploads`** with project scoping, not in `scene` jsonb (M-2, M-14).
4. **Start-up self-checks:** route rules with `level` on simple modules, the audit trigger present, required grants. Report failures as system alerts.
5. **Background jobs with progress** for long operations: range delete, verify, archive restore, large asset delete.
6. **Frontend test runner (Vitest)** for pure helpers: Live Feed `status.ts`, SVG sanitiser, CSV escapers, twin save guards.
7. **External anchoring of the audit-log head** (backup manifest or syslog) to support compliance claims.

## L. Final production readiness assessment

**NOT READY FOR PRODUCTION.**

**Reasoning:**
- No critical vulnerability exists, and the core security controls remain strong.
- However, eight HIGH issues are reachable by ordinary users or normal use:
  - an Engineer can mint an admin-level API credential;
  - an Engineer can destroy data under legal hold;
  - a missing file takes the API down;
  - large plants get rate-limited by their own Live Feed;
  - twin layouts can be silently overwritten.
- Six of these were reported five days ago with a "fix before the next installation" priority and are still open.
- The new audit log is described as a compliance control, but its tamper evidence does not hold against the app's own database login.

Once the P0 items are fixed and re-tested, the platform would move to **CONDITIONALLY READY – REMAINING RISKS DOCUMENTED**.

**Untested areas:**
- Runtime and penetration testing, because no isolated database was available.
- Browser walkthrough: CSP violations, WebGL context loss, real 429 rates.
- nginx, TLS, systemd and journald on a real VM.
- Real PostgreSQL behaviour of the hash round trip, trigger and grants.
- MQTT and Azure broker paths and broker access control.
- Email delivery, PDF rendering, and AI prompt-injection behaviour against the live model.

Per the audit rules, no source code, data or configuration was changed. Fixes start only after these findings are reviewed and approved. Each fix will then get a regression test and a remediation verification report.
