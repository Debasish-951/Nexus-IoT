UI / UX Modernization Proposal

Four design directions for WS-Integrated Suite

Presentation-layer only. Every concept preserves 100% of existing functionality, business logic, APIs, database structures, calculations, validations, integrations and user journeys. Each is a complete, standalone HTML prototype covering six screens in desktop and mobile.

Scope UI/UX only · no backend change Screens 6 per concept · 24 total Standards WCAG 2.1 AA target Date 02 Aug 2026

Executive Summary

The current interface is functional and internally consistent, but reads as mid-2010s in four specific, fixable ways. It is not broadly broken — the component layer (55 Radix/shadcn primitives), the light/dark token system, and the validated colour-blind-safe chart palette are all sound foundations that every concept below builds on rather than replaces.

What is already good and must be preserved

  • One module vocabulary shared between nav, routes and API, served from /security/rbac-catalog so the UI cannot promise access the server refuses.
  • One WebSocket hook with 11 consumers — no per-screen connection sprawl.
  • Light and dark both deliberately designed (not one inverted from the other) as HSL tokens.
  • A validated categorical chart palette — worst adjacent pair ΔE ≥ 12.6 under deuteranopia, with identity (SERIES) separated from state (STATUS) so a normal data series is never painted in an alarm colour.
  • 55 uniform shadcn/Radix primitives — visual inconsistency comes from page-level code, not the component layer, which means a token-level change propagates widely for little effort.

The Four Concepts

Each is a genuinely different design philosophy — not a palette swap. They differ in radius (3 / 10 / 2 / 4px), ground (light / dark / dark / light), navigation model (rail / rail+panel / rail+status band / horizontal), and density (16 / 9 / 22 / 12 rows per screen at 1440×900).

Concept 1 — Meridian · Structured Enterprise

Design philosophy

Treats the screen as an instrument panel. Density is a deliberate feature rather than a compromise: 3px radius, strong 1px rules that group information, one disciplined accent, and tabular numerals wherever figures align in a column. Built for the plant engineer who needs 16 rows visible without scrolling, while staying clean enough that a screenshot lands well in a board deck.

Pros
  • Highest information density of the two light options — 16 rows vs Lumen's 12
  • Pattern language enterprise buyers already recognise (Fiori, ServiceNow, Salesforce)

  • Light-first makes WCAG AA contrast easiest to achieve and hold
  • Screenshots and PDF exports land well in executive material
Cons
  • Can read as austere; least "premium" of the four at first glance
  • Light-first means dark mode becomes the secondary theme, inverting the current preference
  • Dense rules and borders require discipline — sloppy application looks cluttered fast
  • Less differentiated: looks like enterprise software, which is the point but also the limit

Concept 2 — Atlas · Calm Modern SaaS

Design philosophy

Remove every line that is not earning its place. Structure comes from five layered surface elevations rather than a grid of borders. 10px radii, generous 16px padding, roomy 48px rows, and a ⌘K command palette as the primary means of navigation rather than an added convenience. Dark-first, because that is where the product already lives.

Concept 3 — Signal · Operations Control Room

Design philosophy

Stop treating this as a generic SaaS product. It is an industrial telemetry platform, so borrow from the tools engineers already trust: a permanently-mounted 28px system-status band, monospace for every identifier and numeric value, a colour stripe on the left edge of each row, and alarms rendered above all other page content. The only concept where an operator learns system health without clicking anything.

  • Highest implementation effort — needs a new persistent band component and per-row stripe treatment

Concept 4 — Lumen · Executive Light / Editorial

Design philosophy

Built for the person who reviews rather than operates. Borrows from data journalism and management consulting: a Georgia serif display face against a clean sans body, numbered sections, and charts presented as captioned figures with a sentence explaining what they show and what to do about it. Warm paper ground and a single deep-navy accent make it the only concept designed to survive being pasted into a board pack.

Recommended Option

Adopt Meridian as the base system, with Signal's operational patterns grafted onto the operational screens

Meridian wins on the criteria weighted highest for a global enterprise audience: enterprise-buyer familiarity, WCAG achievability, and — importantly for a project constrained to presentation-layer changes — the lowest implementation effort, because it maps almost directly onto the existing shadcn component library and is largely a token, spacing and table-behaviour change rather than a rebuild.

But a single concept applied uniformly would be the wrong answer, because this product has two genuinely different audiences.

Why a hybrid, specifically

The frontend review of this platform identified two distinct personas with opposing needs: operators (Live Twin, Live Feed, Brokers, Alarms — who live in the app and need density plus alarm response) and executives/analysts (Analytics, Reports — who review periodically and need clarity plus export). Optimising for one degrades the other.

Adopt Atlas's ⌘K palette in every case — it is the single highest-value navigation addition and is base-independent. If the decision is instead to keep the current dark-first identity and accept the density cost, Atlas is the defensible second choice, and its migration path is the shortest of the four.

Implementation Approach

Phase 1 scope boundary — presentation layer only

  • No backend changes — no route, middleware, or server-side logic modifications
  • No business logic changes — ingest pipeline, alarm evaluation, expression engine untouched
  • No workflow changes — every user journey keeps the same steps in the same order
  • No API changes — lib/api-spec/src/openapi.yaml untouched; no codegen re-run required
  • No database changes — no schema, migration, or query modifications
  • No calculation, validation or integration changes — the same values, the same rules, the same webhooks
  1. Token layer — rewrite the HSL custom properties in index.css and set --radius. Because 55 shadcn primitives consume these tokens, this alone propagates most of the visual change. no component edits
  2. Shared chrome — page-header component (icon + title + subtitle + action bar), breadcrumb component, and the ⌘K palette. These are additive; existing pages adopt them incrementally. new components only
  3. Table upgrade — sticky headers, density toggle, bulk-action bar, right-aligned tabular numerics, hover row actions, applied once to a shared table wrapper and inherited by every grid. presentation only — same data, same queries
  4. Form layout — introduce the label-left section pattern and sticky footer bar. react-hook-form wiring, validation rules and submit handlers are untouched; only the surrounding markup changes.
  5. KPI and chart enrichment — add delta, sparkline, target bar and the "Reading:" caption slot. Uses data already returned by existing endpoints; no new API calls.
  6. Operational grafts — the Signal status band and per-row status stripes on Live Twin, Live Feed, Brokers and Alarms. Reads from the existing WebSocket stream.
  7. Remove dated decoration — the four tinted icon chips, the dotted graph-paper background, the spring-physics hover, and the permanently-empty "Created By" column.
  8. Accessibility verification — contrast audit both themes, verify status is never colour-alone, confirm keyboard focus is visible on every interactive element, check touch targets ≥ 44px on mobile.

How to review these

Each prototype is a single self-contained HTML file with no external dependencies — no CDN, no fonts to download, no build step. Open any of them directly in a browser (double-click, or file://), or serve the folder over HTTP if you prefer.

  • Use the tab bar to move between the six screens: Dashboard, Landing/Home, Data Table, Form, Analytics, Settings.
  • Use the Desktop / Mobile toggle to see the responsive treatment — mobile is a genuinely different layout (bottom tabs, stacked forms, reflowed KPIs), not a squeezed desktop.
  • Amber annotation bars inside the prototypes call out specifically what each concept changes versus the current build, and why.
  • All content uses your real domain data — EMS, device energy, the 24 declared attributes, 3,386,688 telemetry rows — so the density and layout claims are evaluable rather than notional.
